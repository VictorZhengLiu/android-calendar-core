# 日历重叠日程排版引擎（Java）

把一天中时间重叠的日程排成不互相遮挡的分栏布局。

```
09:00 | 1 |   |
09:30 | 1 | 2 |
10:00 |   | 2 |
```

`1` 是 09:00-10:00 的站会，`2` 是 09:30-10:30 的评审。两者时间重叠，所以各占一栏；`10:00` 之后站会结束，评审继续。

---

## 为什么写这个

日历的日视图里，同一时间段可能有好几个日程。全部按整宽画就会互相盖住，所以必须分栏。这件事看着简单，真做对不容易：

| 常见做法 | 问题 |
|---|---|
| 重叠就平分宽度 | 三个日程各占 1/3，但它们并不两两重叠，浪费了 2/3 |
| 每层各自分栏 | 第 1 层的日程会盖住第 0 层里时间冲突的日程（跨层栏位复用） |
| 整宽拉伸填充空档 | 长日程会盖住右侧时间不冲突、但视觉上被压在下面的短日程 |

这个引擎的做法是：**用 Δt 相位分层决定纵向节奏，用全组共享的栏位池决定横向归属，并保证一条硬性不变量——时间重叠的两个日程，横向范围绝不相交。**

## API

```java
List<LayoutEvent> day = List.of(
        LayoutEvent.at("a", "站会",  "09:00", "10:00"),
        LayoutEvent.at("b", "评审",  "09:30", "10:30"),
        LayoutEvent.at("c", "复盘",  "10:15", "11:00"));

EventLayoutEngine.Result result = new EventLayoutEngine().layout(day);

for (PlacedEvent placement : result.placements()) {
    double left  = placement.leftFraction();    // 左边缘，占宽比例
    double width = placement.widthFraction();   // 宽度，占宽比例
}
```

### `LayoutEvent`

| 工厂方法 | 说明 |
|---|---|
| `at(id, title, "09:00", "10:00")` | 定时日程，参与分栏 |
| `timed(id, title, TimeInterval)` | 同上，用 `TimeInterval` 构造 |
| `allDay(id, title)` | 全天日程，**不参与分栏**（另有横条区域渲染） |

事件按 `id` 区分身份，不按时间。同一时间的两条日程是两条，不会合并。

### `PlacedEvent`

| 方法 | 说明 |
|---|---|
| `column()` / `columnSpan()` | 零基栏位下标与跨栏数 |
| `totalColumns()` | 所属组的栏数（宽度的分母） |
| `leftFraction()` / `widthFraction()` | 已算好的比例，直接用 |
| `layer()` / `isSpilled()` | 所在层，以及是否因冲突被下移 |
| `conflicts()` | 与该事件时间重叠的全部日程 |

### `EventLayoutEngine.Result`

| 方法 | 说明 |
|---|---|
| `placements()` | 所有定位结果 |
| `placementOf(event)` | 按事件取定位，全天日程返回 `null` |
| `groups()` | 冲突分组，含每组的层与分块结构 |
| `maxColumnsAnywhere()` | 最忙的一组用了多少栏 |

### 校验器

```java
List<EventLayoutEngine.Violation> violations = EventLayoutEngine.validate(result);
```

`validate` 是**公开 API**，不是测试专用。它检查那条核心不变量。之所以暴露出来，是因为这个保证是引擎存在的全部意义——调用方（以及测试）应该能直接断言它，而不是手工比对栏号。

## 保证与取舍

### 保证

**时间重叠的两个日程，横向范围绝不相交。**

不是"通常不会"，是构造上不可能：栏位分配在**整组范围内**检查冲突，而不是在层内。这条保证让渲染器可以把每个日程当作一个普通矩形，按任意顺序绘制。

### 取舍

**1. 每个日程恰好占一栏，不做横向拉伸。**

一个"列号 + 跨度"的布局无法表达"上宽下窄"。所以一个 09:00-17:00 的长日程，若旁边有两个只在上午的短日程，长日程保持自己那一栏，而**不会**向右延伸到短日程下方。

代价是留白，换来的是渲染器可以依赖的不变量。

> 这个决定是量出来的，不是拍脑袋的：加了"只在栏位完全空闲时才拉伸"的规则后，20 万次随机日程里 `columnSpan > 1` 出现 **0 次**——因为栏位池只在有日程需要时才创建，永远不存在空栏可拉伸。所以拉伸代码是**不可达的死代码**，直接删掉，而不是留着当装饰。

**2. 同一相位的日程过多时会向下顺延。**

层 = Δt 相位桶，层号对应真实时间偏移（第 L 层从 `groupStart + L*Δt` 开始）。同一相位里若冲突日程多于该层能容纳的数量，多出来的会移到下一层。

这**不影响横向正确性**，但会让某些日程所在的层比它的开始时间早。所以每个定位结果带 `isSpilled()` 标记，渲染时按日程**自己的开始时间**定位纵坐标，而不是按层的顶边。

**3. 组与组之间不共享栏位。**

上午很挤不会让下午的日程变窄。代价是同一天不同时段的日程宽度可能不一致——这在日历应用里是预期行为。

## 算法

### ① 分组（传递冲突）

按开始时间排序扫一遍，用一个"当前组最大结束时间"维护分组边界：

```
09:00-10:00 ┐
09:30-10:30 ├─ 一组（中间事件把它们串起来）
10:15-11:00 ┘
```

首尾不重叠的第一个和第三个仍然同组，因为第二个事件把冲突传递过去了。拆开的话，10:15 的日程会拿到整宽，而 10:00 附近的日程只有半宽，视觉上像 bug。

首尾相接（`10:00` 结束、`10:00` 开始）**不算冲突**——区间是半开的 `[start, end)`，背靠背的日程可以共用一栏。

### ② 分层（Δt 相位桶）

`Δt` 默认 **45 分钟**（可配置）。事件的相位 = `(开始时间 - 组内最早开始时间) / Δt`，层号就是相位。

同一层放不下冲突日程时顺延到下一层，保证同层内任意两个日程都不冲突。

### ③ 层内排序与分块

层内按优先级排序，然后分成三类块：

```
优先级：冲突日程数（降序） → 开始时间 → 时长 → 标题
```

| 块类型 | 含义 |
|---|---|
| `SPILLED` | 放不进自己相位、被下移的日程 |
| `CONFLICTING` | 本层需要多栏的原因，即互相冲突的日程 |
| `FREE` | 本层里不冲突的日程 |

按冲突数降序排，是为了让密集区域的栏位分配在输入顺序变化时保持稳定。

### ④ 栏位分配

**全组共用一个栏位池。** 按优先级顺序处理，每个事件放进第一个「与池中所有已就位事件都不冲突」的栏；没有可用栏就新建一栏。

这是区间图上的贪心着色。区间图是完美图，贪心 first-fit 能达到最优——所以栏数**恰好等于峰值并发数**，不是估计值。测试里直接断言了这一点。

## 最大分栏数（独立工具方法）

```java
int peak = EventLayoutEngine.maxConcurrent(groupEvents);
```

经典的"会议室"扫描：按开始时间排序，用小顶堆维护活跃结束时间，弹出所有已结束的，堆的峰值就是答案。用于测试校验。

## 测试

**41 个测试**，全部离线可运行。

核心思路：**每个场景都断言 `validate` 通过**。分栏引擎真正的失败不是"栏号算错"，而是"两个时间重叠的日程被画在了一起"。所以先用不变量兜底，再断言具体栏号保证布局可读。

几类值得注意的测试：

- **跨层冲突**（`aLaterConflictingEventIsNeverSeatedOnTopOfAnEarlierOne`）—— 这个引擎最初就是被这个 bug 逼着重写的：按层分配栏位时，第 1 层的日程会用到第 0 层冲突日程已占的栏
- **任意顺序等价**（`layoutDoesNotDependOnInputOrder`）—— 布局不应取决于调用方传入的顺序
- **全天日程排除**、**空白天**、**跨整天日程**、**同一时刻的两条日程**
- **随机化不变量检查**（`randomisedDaysKeepEveryInvariant`）—— 用**固定种子**跑 3000 个伪随机日程，断言四条不变量：无重叠、每个事件恰好定位一次、栏号在范围内、栏数不超过峰值并发

固定种子的意义是：失败可复现。手写用例只能覆盖作者想到的情况，随机化补的是想不到的那些。

## 开发过程中被测试推翻的 4 个设计

这段比最终代码更有价值：**排版算法的错误几乎总是"看起来能跑"**，只有把它们逼出来才会暴露。

### 1. 按层分配栏位 → 跨层覆盖（严重）

最初每层各有一个栏位池。`A 09:00-10:00`、`B 09:30-10:30`、`C 10:00-11:00` 里，B 和 C 被分到不同的层，C 就被放进了 B 已占用的栏——它们**时间重叠**，画出来就是 C 盖住 B。

修法：栏位池提升到**整组共享**，分配时与所有已就位事件比较冲突。

### 2. 宽度分母用了栏位池的大小

池子里有稀疏空洞时（某层没坐到那个编号），分母被算大，所有日程宽度都偏窄。修法：分母改为**实际被占用的最高栏号 + 1**。

### 3. 拉伸逻辑的边界失控

改成稀疏栏位池后，"向右拉伸直到遇到被占栏位"变成一个**没有上界的循环**，因为稀疏池里存在永远不会被占用的栏号。这个 bug 表现为**进程挂死**。

修法：加上栏数上界。然后一测量，发现加上界后拉伸**永远触发不了**，于是把整段删掉（见上文"取舍 1"）。

### 4. 分层方向搞反

早期版本试图把日程"上提到更早的层"来省宽度，结果会把 09:25 的日程画到 09:00 的位置——纵向错位。改成**只能向下顺延**，并用 `isSpilled()` 显式标记，让渲染方按真实开始时间定位。

## 与"参考实现"的关系

这个模块的**思路**受限于一个真实的系统日历项目：那里的日视图同样使用「Δt 相位分层 + 冲突块/无冲突块/并列块 + 栏位分配」这套结构，也追求和 Google Calendar 一致的排列效果。

但**代码是独立实现的**：没有参考、复制或翻译任何原项目代码，分层与拉伸的规则、栏位池的作用域、以及碰撞处理都与原设计不同（原设计的"并列块上提"在这里被论证为不适用并被替换掉了）。上文的取舍和缺陷复盘都是本次实现自己的记录。
